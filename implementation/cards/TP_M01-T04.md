## Outcome

Define a repeatable paired disabled/enabled effectiveness benchmark and a quality/regression matrix strong enough to decide whether custom pruning is worth carrying.

## Scope

### Included

- choose measurable request-context/token metric available on the current baseline;
- define representative deterministic tool-heavy histories/fixtures;
- define paired comparison method on identical history;
- define what counts as material reduction and how the threshold will be selected/justified;
- define continuation/regression cases for verbose successful output, prior failures, patch/change evidence and current compaction/context-management interaction;
- define pass/fail evidence required by TP_M03.

### Excluded

- implementing the benchmark harness;
- running performance experiments beyond small source-grounding checks needed to prove measurability;
- setting a product threshold without evidence;
- pruning implementation.

## Constraints

- Context reduction cannot be the sole acceptance dimension.
- Comparison must hold conversation/tool history constant between disabled/enabled cases.
- Metrics must correspond to actual request input or the closest validated equivalent; avoid misleading repository-size/log-size proxies.

## Acceptance

- measurable metric and collection method are explicit;
- representative fixtures cover R20/R21 scenarios;
- paired comparison and material-benefit decision rule are defined;
- regression matrix has explicit observable pass/fail criteria;
- TP_M03 can implement/run the benchmark without inventing product semantics.
